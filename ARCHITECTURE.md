# Architecture

How the game is put together, what each part may and may not do, and the contracts the V1 iterations code against. The plan itself is `docs/V1_PLAN.md`. Update this file in the same commit as any change to a boundary or interface described here.

See [Steam and co-op platform plan](docs/PLATFORM.md) for the implementation sequence, compatibility boundaries and benchmark results.

Findings that shaped the plan:

- **No simulation existed.** Time of day was a number advanced by frame time. Nothing was deterministic, and visual code used `Math.random()` freely (fine for particles, not for world truth).
- **The world did not save.** Terrain edits and felled trees were lost on reload; only buildings persisted, in build mode's own storage.
- **Buildings have no materials or physics.** A wall is a type string on a grid edge; wall and floor "materials" are appearance names. Wood and stone are two counters.
- **The engine and add-ons are already decoupled** through `window.__game`, `window.__build` and `window.__nature`. That boundary is kept.
- **Performance.** The page targets 144 fps on a desktop GPU. Chunk building is time-budgeted per frame; the simulation follows the same rule (see below).

## The three layers

```
 input ──► commands ──►  SIMULATION  (src/sim/)      truth, deterministic, headless
                              │  state (plain data) and events
                              ▼
                        WORLD BRIDGE (engine.js, build.js)   terrain, pieces, saving
                              │
                              ▼
                         RENDERING (engine.js, nature, fx)    draws state, owns nothing
```

1. **Simulation (`src/sim/`).** All world truth that changes over time: the clock, and from wave B on weather, materials and stock, structure, heat, power, water, soil, plants, animals, food. Pure JavaScript modules with no DOM, no three.js, no wall clock. They run identically in the page and in Node.
2. **World bridge.** The engine and build mode own the *shape* of the world (terrain heights, where pieces stand) and expose it to the simulation as plain data. They also do the saving.
3. **Rendering.** Reads simulation state and draws it. May interpolate, animate and use `Math.random()` for cosmetics. Must never be the only place a fact lives: if it matters after a reload, it belongs in simulation state.

**The rule that keeps this honest:** delete every renderer and the simulation must still produce the same world. The headless tests do exactly that.

## Engine and game: keeping the engine reusable

The owner wants to reuse this engine for other games (the archived `combat` branch is one). So every feature is built in two parts: a **generic mechanism** that knows nothing about homesteading, and **content** that configures it. The test for a generic module: could a different game use it unchanged by supplying different data?

| Generic mechanism (engine) | Homestead content (game) |
|---|---|
| Simulation core: ticks, state, commands, seeded randomness, save and migrations | The list of systems registered for this game |
| Calendar, sun and weather model | Climate presets |
| Materials and items registry format, stock and money | The actual materials, items and prices |
| Pieces, fixtures, ports and connections; network solving for flows | Catalogs of panels, tanks, pumps, stoves |
| Individual-animal framework: traits, inheritance, energy and water budgets | Chickens, goats, breeds |
| **Vehicles: a body, a drive model, seats, attachment points, and implements that perform a work function** | Mini excavator, skid steer, their buckets, forks and augers, rental rates |
| Carrying, the hold-to-work action, staged assembly of ghosts | Construction stages, the shed tutorial, how-it-goes-together cards |
| Terrain editing, trenches as terrain plus a run | Frost depth rules, sewer fall rules |
| Overlays framework | Which overlays exist and how they are coloured |
| Build and plan tools, snapping, selection, inspector | Wall styles, framing methods, plans in the plan book |

Rules:

- A generic module contains no homesteading words, catalog ids, prices or tutorial text. It takes them as data or callbacks.
- Content lives in its own files (catalogs, presets, plans, card text) and may be replaced wholesale.
- A generic module does not import a content module. Content registers itself with the mechanism.
- New generic modules are named for what they are (`vehicles.js`, `carry.js`, `assembly.js`, `networks.js`), not for their first use.
- Vehicles in particular: one drive model and controller for any wheeled or tracked body; a vehicle is a data record (dimensions, mass, speed, turning, seats, attachment points); an implement is a data record plus a work function (dig, grade, lift, drill). An excavator is content. A cart, a tractor, a truck or a boat in another game should need only new records.
- File layout: `src/engine/`, `src/game/`, `src/sim/core/` and `src/sim/content/` exist, and most older files still sit in `src/` and `src/sim/`. New generic modules go in `src/engine/` (page side) and `src/sim/core/` (simulation side); new content goes in `src/game/` and `src/sim/content/`. The tidy-up that moves the older files into that layout was promised for after wave C. It has not happened and is deferred to a quiet window, when no other session is editing those files; until then, do not move files to match the layout.
- Definition of done for any iteration now includes: the mechanism and the content are in separate files, and the mechanism passes its tests with a non-homestead test fixture.

## Simulation core

`src/sim/sim.js`. One state object, advanced in fixed ticks.

- **Units.** SI throughout, and time in seconds of world time. State field names carry the unit when it is not obvious (`litres`, `tempC`, `kWh`). No unitless "stats".
- **Tick.** `TICK` = 60 s of world time. A day is 86,400 s (1,440 ticks). A new world starts at 08:10 on day 1.
- **State.** `{ v, seed, tick, t, rng, sys }`, plain JSON. `sys[name]` is each system's state. Nothing else holds simulation truth.
- **Systems.** `{ name, every, init(ctx), step(ctx), commands }`, registered in `GAME_SYSTEMS` in `src/sim/index.js`, in dependency order. Today: `weather, streams, stock, site, structure, routes, services, electrical, parts, plumbing, water, thermal, cooking, chickens, physical-kitchen, ground, landscape, garden, construction, foundation, vehicles` (construction is no longer last: `foundation` and `vehicles` follow it). A system runs when `tick % every === 0`, and always receives the same `ctx.dt = every × TICK`, so its numerical behaviour never depends on frame rate or game speed. Choose the slowest cadence that is physically adequate: weather hourly-ish, heat every few minutes, plant growth a few times a day.
- **Context.** `ctx.s` is the system's own state; `ctx.get(name)` reads another system's state (read only by convention; write only your own); `ctx.rng(name)` is a seeded stream; `ctx.emit(type, data)` tells the renderer something happened.
- **Randomness.** Only through `ctx.rng()`. Stream positions are saved, so a loaded game continues the same sequence.
- **Commands.** Player and game actions enter with `sim.command(name, payload)` and apply at the start of the next tick. Systems declare handlers in `commands`. This is what makes a session replayable and is what the build journal and time-lapse will record.
- **Events.** `sim.listen(fn)` for one-way notifications to rendering and audio. Events carry no truth.
- **Advancing.** The page calls `sim.advance(worldSeconds, maxTicksPerFrame)` once per frame. Whole ticks run; the remainder waits. If a frame cannot afford the ticks owed (top speed on a slow machine), the excess is dropped: time runs slower, nothing stalls, determinism holds.
- **Speed.** Pause, 1×, 10×, 100×, 1000×. At 1× a day takes 20 real minutes; at 1000× about a second. Pause stops world time only: the player can still walk and build.
- **Cost budget.** The simulation gets at most 1 ms of a 6.9 ms frame at 144 fps. At 1000× that is about 8 ticks per frame, so a full tick of all systems must average under ~0.1 ms. Systems that cannot meet that run on a slower cadence or amortise work across ticks. Spatial fields (soil, heat) use coarse grids sized to the homestead, not the world.
- **Conservation tests.** Every physical system ships a headless test that checks a conserved quantity or known relationship over a long run (energy in = stored + lost; water in = stored + used). `test/sim.test.mjs` shows the pattern.

### World time and the engine

`world.time` in the engine is now a view of the simulation clock (fraction of a day). Reading it is free. Setting it moves time *forward* to the next moment the clock shows that time; time never runs backwards. Sheltered resting and the screenshot tools use this.

## Saving

`src/sim/save.js`. One JSON document per world seed in `localStorage` under `homestead:save:<seed>`:

```
{ format: "homestead-save", v, sim: <simulation state>, world: { removed, wood, stone, player, cam, builds } }
```

- Autosaves every 20 s and when the page is hidden or closed. The last world played reopens on load.
- `SAVE_VERSION` and `MIGRATIONS` in `save.js`: any change to the shape of a save adds a migration. A save from the previous wave must load.
- Terrain edits live in the simulation (`sys.ground.macro`, see "One ground" below); save v3 moved the old `world.edits` (base64 `Float32Array` tiles) there.
- Save v4: build mode's Equip wires and water pipes became legacy runs in `sys.routes` (`src/sim/services-legacy.js`, converted on the page once build mode has them, ids kept); only flues are build mode links now.
- Every earthwork-format grid anywhere in the state is packed when stored (`src/sim/core/earthwork-codec.js`, save v2): `stringifySave(save)` uses `packReplacer`, `readSave` uses `unpackReviver`, so packed and plain saves both load and the in-memory shape never changes. About 17 KB to 1-2 KB a dug 3.2 m tile; flat machine tiles about 0.1 KB. `__game.saveSize()` reports `{ bytes, plainBytes }`. The engine's autosave hands `sim.state` by reference (no deep copy); `__game.saveData()` still returns a copy.
- Editable buildings are saved in `world.builds`. Build mode keeps `world-engine-build:1:<seed>` as a legacy fallback. Loose objects in flight (falling trees, logs, pickups) are not saved.
- New systems get saved automatically, because their state lives in `sim.state.sys`.

## The piece interface

Structure, heat, salvage, contractors and blueprints all need to read buildings without knowing how build mode stores them. They read **pieces**: every built element as plain data. As built in iteration 2a:

```
piece = {
  id,          // "p12": persistent. Survives save and load, undo and redo, and never shifts when other pieces come or go.
               // Parts of one element share its id with a suffix: "p8.0" a roof plane, "p8.g0" its gable infill, "p8.rb" its ridge beam,
               // "p3.s4" a tower side, "p3.f0" a tower floor, "p3.r" its roof, "p3.st" its stair, "p5.fd" the footing under floor p5, "p7+p9" the beam between two pillars.
  struct,      // the structure it belongs to (persistent number); storey: its storey there (-1 cellar, 0 ground, 1..)
  kind,        // "wall" | "floor" | "roof" | "door" | "window" | "post" | "beam" | "stair" | "tower" | "foundation" | "path" | "fixture"
  type,        // build mode's own name: wall "wall" | "rail" | "gable"; roof "gable" | "hip" | "shed" | "flat" | "cone" | "dome" | "pyramid";
               // door "door" | "door2" | "railgate"; window "window" | "window2" | "window4"; post "pillar" | "chimney"; stair "straight" | "spiral"; fixture: the furniture name
  material,    // build mode's appearance name until the orchestrator maps it through APPEARANCE_MATERIAL
  a, b,        // world metres { x, z }: wall and beam ends, a roof plane's eave edge, a stair's foot and head, opposite corners of a floor; a point piece has a = b
  y0, y1,      // bottom and top in world metres (right for upper storeys, stretched storeys, raised floors and turned structures)
  length, height, thickness, area,   // whichever apply, metres and square metres. A wall's area is its whole face; netArea leaves out its openings.
  layers,      // walls, floors, roofs, doors, windows: [{ material, thickness, role }] from the outside in (floors from the underside up)
  openings,    // walls: [{ id, kind: "door" | "window" | "opening", type, offset (m along the wall from a), width, sill, height, y0, y1, area, fill }]
               // doors and windows are also pieces of their own, with wall: the id of the wall they are in. An "opening" is an open arch: no id, no piece.
  // floors: outline and holes (world corner loops), perimeter. Roof planes: footprint, pitchDeg, planArea, eaveY, ridgeY, facing { x, z } (downslope), roof: the roof's id.
  // towers: radius, sides, storeys, parts: [ids]; their parts carry tower: id. Fixtures: name, width, depth, rotationRad. Paths: width.
}
```

- `window.__build.pieces()` returns the list (cached until something changes: treat it as read only); `piece(id)` finds one; `quantities(list?)` totals wall length, floor and roof area and counts.
- `window.__build.version` changes whenever any structure changes; `onChange(fn)` calls `fn(version)` at most once a frame when it has, and returns a function that stops it.
- `window.__build.serialize()` gives every building as plain JSON (`{ format: "homestead-buildings", v: 2, nextStruct, nextPiece, structs }`) and `restore(data)` puts it back exactly, ids included; version 1 saves (no ids) load and are given ids. Build mode still keeps its own copy under `world-engine-build:1:<seed>`; the world save can take over by calling these two.
- **How identity works.** Roofs, towers, stairs, pillars, paths and furniture store their id. Walls and floors are stored as 1 m edges and tiles, so a wall piece is a straight run of edges of one kind and material, and a floor piece is a connected area of one surface. Each run or area keeps the id most of its parts already had; a part split off (or a wall repainted in part) is a new piece. Changing a door or window to another type makes a new piece.
- **Layers.** Each appearance implies a default build-up (`window.__build.ASSEMBLIES`; the plain material names used are in `LAYER_MATERIALS` for the registry to map). `setLayers(id, layers | null)` stores a different build-up for one piece; it is saved with the building and follows the piece through copies and splits.
- Not yet: `supports` (iteration 3) and `condition` (18). A chimney is a `post` of type `chimney`. Tower landings above the ground floor report the inner deck as `outline` and the landing strip as `landingArea`.
- A piece is the same piece for its whole life: built, removed, stored, sold, reinstalled. Its properties never change with where it is.

## Wave B contracts

Three iterations run in parallel in wave B. Each owns the files listed and touches shared files only where stated.

### Iteration 1: calendar, sun and weather

Owns `src/sim/calendar.js`, `src/sim/weather.js`, `src/weather-view.js` (add-on), `test/weather.test.mjs`. In `src/engine.js` it may change only `updateSky()` and the sky constants beside it.

- `calendar.js` exports pure functions of world time `t` and a site `{ latitudeDeg }`: `dayOfYear(t)` (0..364, 365-day year), `yearIndex(t)`, `season(t)` ("spring" | "summer" | "autumn" | "winter"), `dateText(t)`, `sunPosition(t, site)` -> `{ elevationRad, azimuthRad }` (azimuth clockwise from north), `dayLengthHours(t, site)`, `clearSkyIrradiance(t, site)` -> `{ directNormalWm2, diffuseWm2, globalHorizontalWm2 }`. A new world starts on a spring date; `START_T` in `time.js` stays the zero point and calendar adds a start-of-year offset.
- System `weather`, state `sim.state.sys.weather`:
  `{ site: { latitudeDeg, climate }, tempC, humidity (relative, 0..1), dewPointC, windMs, windDirRad, cloud (0..1), rainMmH, snowMmH (water equivalent), snowDepthM, pressureHPa, solar: { directNormalWm2, diffuseWm2, globalHorizontalWm2 }, groundTempC (deep soil, slow), ...internal generator state }`
  Other systems read these fields with `ctx.get('weather')`. Field names and units are fixed from here on.
- Engine world +x is east and +z is south for sun azimuth.
- Delivered (iteration 1): `windDirRad` is the direction the wind blows *from*, clockwise from north (meteorological). Extra calendar exports: `sunTimes(t, site)` -> `{ sunriseH, sunsetH, solarNoonH, dayLengthH }`, `solarDeclinationRad`, `monthOf`, `dayOfMonth`, `dailyInsolationTOA`. Weather extras: `CLIMATES` presets (`temperate` default at 45 N, `mediterranean-coast`, `cold-continental`), command `weather.setSite { climate?, latitudeDeg? }`, internal `gen`, `snowSweMm`, `snowDensityKgM3`, `totals`.

### Iteration 2: materials, items and inventory

Owns `src/sim/materials.js`, `src/sim/items.js`, `src/sim/stock.js`, `src/stock-view.js` (add-on), `test/materials.test.mjs`. In `src/engine.js` it may change only the `world` object's `wood` and `stone` fields (into views of the stock, the way `time` is a view of the clock), the tree-felling and pickup functions, and the HUD stock lines.

- `materials.js` exports `MATERIALS`, a frozen map `id -> { id, name, class ("wood" | "masonry" | "metal" | "insulation" | "glass" | "roofing" | "earth" | "membrane" | "fabric"), densityKgM3, conductivityWmK, specificHeatJkgK, bendingStrengthMPa?, compressiveStrengthMPa?, elasticModulusGPa?, embodiedNote? }` with real published values, and `material(id)`. It also exports `APPEARANCE_MATERIAL`, mapping every build-mode appearance name (wall, floor, roof and path surfaces in `src/build.js`) to a registry id.
- `items.js` exports `ITEMS`, a frozen map `id -> { id, name, category, unit ("each" | "m" | "m2" | "m3" | "kg" | "L"), material?, massKgPerUnit, priceUsd, dims? }` covering lumber sizes, logs, sheet goods, insulation, roofing, fasteners, glass, stone, hand tools and power tools.
- System `stock`, state `sim.state.sys.stock = { money, items: { [itemId]: quantity }, tools: [...], projects: [...] }`. Commands: `stock.add`, `stock.remove`, `stock.buy` (fails cleanly if unaffordable), `projects.add`, `projects.done`, `projects.dismiss`. Mass and money are conserved by every command.
- As built: material classes also include `"fluid"` (water, air). Glazing assemblies carry `uValueWm2K` and `thicknessM`. `APPEARANCE_MATERIAL` is a flat name map; `APPEARANCE_BY_KIND` is the same by wall/floor/roof/path (shared names such as `dark`, `tile`, `cobble` map to the same material in every table). Tools live in `stock.tools` (single, unconsumed); `world.wood` and `world.stone` are the stock items `wood` and `stone`; felled logs add `log_pine` / `log_birch` / `log_oak` (m3, from real trunk volume). Add-ons use `window.__game.stock` (`state`, `do(command, payload)` for instant, replay-recorded commands, catalog and helpers) and `window.__game.powerAvailable()`.
- Power tools declare `powerW`; whether power is available is asked through `window.__game.powerAvailable()` (returns false until the electrical iteration).

## Wave C contracts

Six iterations run in parallel. Every system reads buildings only through pieces, weather only through `ctx.get('weather')`, and materials only through `material(id)`. Each owns the files listed. Shared files (`src/sim/index.js`, `build.sh`, `template/head.html`) get one added line or block each. No iteration edits `src/engine.js` except to add a name to `window.__game`; if a system needs something from the engine, it asks for it through a name there.

**Bridging pieces into the simulation.** Pieces live in build mode, outside the simulation. The orchestrator provides `src/sim/site.js`: a `site` system whose state holds a plain-data snapshot of what is built, refreshed by the command `site.setPieces` before the page advances simulation or saves, when the build version has changed. Systems read `ctx.get('site').pieces` and `ctx.get('site').version`. Headless tests construct pieces by hand with the helpers in `test/helpers/pieces.mjs`. Equipment that is not a building piece (a panel, a tank, a stove, a coop feeder) is placed through the same mechanism: it is a piece with `kind: "fixture"`, a `fixture` id from the fixtures catalog, and `ports` describing its connections.

**Fixtures and connections.** A fixture piece is `{ id, kind: "fixture", fixture: <catalog id>, a: { x, z }, y0, y1, yawRad, settings: {...}, ports: [{ id, type: "power" | "water" | "flue" }] }`. A connection is a piece of kind `"wire"` or `"pipe"`: `{ id, kind, from: { piece, port }, to: { piece, port }, lengthM, gauge | diameterMm, material }`. Each system that needs equipment exports its catalog from its own `fixtures-<system>.js` as `FIXTURES_<SYSTEM>`: a frozen map `id -> { id, name, category, system, ports: [...], priceUsd, massKg, dims: { w, d, h }, ...ratings in SI units }`. The orchestrator merges the catalogs into `src/sim/fixtures.js` and the supplier. Systems find their equipment by filtering `ctx.get('site').pieces` for their fixture ids; nothing else tells a system what exists. Test helpers: `test/helpers/pieces.mjs` (`house()`, `setSite()`, `fixture()`, `link()`).

**As built in wave B, for wave C to rely on.** Pieces arrive in `ctx.get('site').pieces` with `material` and every `layers[].material` as registry ids (`appearance` keeps build mode's name; `unknownMaterial` flags anything unresolved). Walls carry `openings`, `area`, `netArea`; roofs come as one piece per plane with `pitchDeg`, `area`, `planArea`, `footprint`, `facing`, `eaveY`, `ridgeY`; floors carry `outline` and a derived `foundation` piece; see the piece-interface section for the full list. `site.version` increases on every change. Wood strengths in the registry are on two bases, marked `strengthBasis` ("characteristic" or "clear-wood-mean"): convert to a design value from the basis. `weather.windDirRad` is the direction the wind blows from, clockwise from north. Commands issued by the interface use `sim.commandNow`, so they apply even while time is paused.

**Overlays.** Each system that has an overlay exposes pure data for it (`overlayData(state)`), and one shared add-on, `src/overlays.js`, owned by the orchestrator, draws whichever overlay is selected. Systems do not draw.

**Units in state.** Temperatures `...C`, power `...W`, energy `...Wh` or `...kWh`, water `...L`, flow `...Lmin`, pressure `...kPa`, force `...N`, stress `...MPa`, lengths metres.

### Iteration 3: structural loads

Owns `src/sim/structure.js`, `test/structure.test.mjs`. System `structure`, cadence: recompute only when `site.version` or snow depth band or wind band changes.
State: `{ version, members: { [pieceId]: { load: { deadN, liveN, snowN, windN }, demand, capacity, utilisation (0..1+), governs ("bending" | "compression" | "deflection" | "bearing" | "uplift" | "unsupported"), supports: [ids], ok } }, foundations: { [pieceId]: { bearingKPa, allowableKPa, ok } }, worst, issues: [{ pieceId, severity, reason, fix }] }`.
Loads follow real practice: dead load from material density and geometry; floor live load 1.9 kPa; roof snow from `weather.snowDepthM` and snow density, with a design value so a structure is judged before the storm arrives; wind pressure from `0.613 * v^2` Pa with a design gust. Load paths: roof to walls, posts and beams, to floors, to foundation and soil. `issues[].reason` and `fix` are plain-language sentences for the inspector.

### Iteration 4: rooms and thermal model

Owns `src/sim/rooms.js`, `src/sim/thermal.js`, `test/thermal.test.mjs`. 
`rooms.js` is pure: `findRooms(pieces)` -> `[{ id, floorAreaM2, volumeM3, heightM, envelope: [{ pieceId, areaM2, toRoom | "outside" | "ground", orientationRad, openings: [...] }], enclosed (bool), leaks: [reason] }]`. A space that is not closed (missing wall, no roof) is reported as not enclosed with the reason.
System `thermal`, cadence 5 minutes. State: `{ rooms: { [roomId]: { tempC, massTempC, humidity, enclosed, uaWK, infiltrationAch, solarGainW, internalGainW, heatingW, lossW: { walls, roof, floor, windows, infiltration } } }, version }`.
Per-room heat balance as a two-node model (air, and thermal mass from the assembly heat capacity): conduction through each assembly from its `layers` (series R-values plus surface films), windows by U-value, ground-contact floors against `weather.groundTempC`, infiltration from an air-change rate that rises with wind and openings, solar gain through glazing from `weather.solar` and the sun's angle on each window, internal gains supplied by other systems through the command `thermal.setGain({ roomId, source, watts })`. An unenclosed space tracks outside air. Energy is conserved: the test checks stored energy change equals gains minus losses.

As built: `findRooms(pieces, { groundHeightAt? })` also gives each room `storey`, `floorIds`, `stackHeightM`, `floorY`, `topY`, `openAreaM2`, `internal` (mass inside the room) and `cells` (for `roomAt(rooms, x, z, y)`); each envelope surface also has `kind` ("wall" | "roof" | "floor" | "ceiling"), `tiltRad`, `layers` (far side to room side) and, on its openings, `{ pieceId, kind, areaM2, layers, open }`. `toRoom` is another room's id, `"outside"` or `"ground"`. Room ids are `"r:" + floor piece id` (`#2`, `#3` where one floor holds several rooms). Pieces with `built: false` are ignored; an opening whose door or window is unbuilt is a hole. Rooms joined by an archway or an open stairwell are one room. Without terrain heights, a floor on a plinth and everything on a cellar storey (`storey < 0`) count as against the ground.
Thermal state also holds, per room, `dewPointC`, `toRoomsW`, `ventM2`, `radiantW`, and at the top `gains`, `heat`, `vents`, `radiant` (what the commands stored). `lossW.windows` includes doors. Commands: `thermal.setGain({ roomId, source, watts, heating?, radiant? })` (`heating: true` counts toward `heatingW`; `radiant` is the share landing on surfaces, default 0.5) and `thermal.setVent({ roomId, source, areaM2 })` (a hole to outside air: an open window or vent). Readers take the whole `sim.state`: `roomModels(state)`, `roomIdAt(state, x, z, y)`, `overlayData(state)` (exported from `index.js` as `thermalOverlayData`). Calendar calls use `ctx.ct ?? ctx.t`.

### Iteration 6: electrical

Owns `src/sim/electrical.js`, `src/sim/fixtures-electrical.js` (catalog entries), `test/electrical.test.mjs`. System `electrical`, cadence 1 minute.
State: `{ circuits: [...], sources: { [id]: { kind, ratedW, outputW } }, batteries: { [id]: { capacityWh, storedWh, voltageV, chargeW, soc } }, loads: { [id]: { ratedW, on, drawW, served } }, busV, generationW, demandW, unservedW, wires: { [id]: { currentA, ratingA, ok } }, today: { generatedWh, usedWh, wastedWh } }`.
Solar output from `weather.solar`, panel area, tilt and azimuth (direct beam by incidence angle plus diffuse), cell temperature derating, and system losses. Batteries with round-trip efficiency, depth-of-discharge limits and charge-rate limits. Loads shed in priority order when supply and storage fall short. Wire current against ampacity for the gauge, breakers trip on overload, voltage drop reported. A generator burns fuel at a real specific consumption. Works at 12 V and at 120/240 V. Energy is conserved: generated = used + stored + losses + curtailed.
Other systems register loads with the command `electrical.setLoad({ id, ratedW, on, priority })` and read `loads[id].served`. Exposes `powerAvailableAt(state, pieceId)` for power tools.

### Iteration 7: water

Owns `src/sim/water.js`, `src/sim/fixtures-water.js`, `test/water.test.mjs`. System `water`, cadence 1 minute.
State: `{ tanks: { [id]: { capacityL, storedL, elevationM, overflowL } }, catchments: { [id]: { areaM2, efficiency, inflowLmin } }, pumps: { [id]: { on, ratedW, headM, flowLmin } }, taps: { [id]: { open, pressureKPa, flowLmin, served } }, wells: { [id]: { depthM, yieldLmin } }, greywater: { storedL }, today: { collectedL, usedL, overflowL } }`.
Roof catchment from `weather.rainMmH` times roof plan area times a runoff coefficient (1 mm on 1 m2 is 1 L), snow contributing as it melts. Static pressure from elevation head (9.81 kPa per metre); a tap below the tank's water level flows by gravity, one above it needs a pump. Pipe friction as a simple head loss per metre by diameter and flow. Pumps draw power through `electrical.setLoad`. Freezing: exposed tanks and pipes can freeze when cold enough for long enough, reported as an issue before it happens. Water is conserved: collected + pumped = stored + used + overflow.
Other systems draw water with the command `water.draw({ id, litres })` and get the amount actually supplied.

### As built in iteration 2a, second half: construction, equipment

`src/framing.js` is a pure generator (`globalThis.__framing`, tested headlessly in `test/framing.test.mjs`); `src/build.js` ties it to the structures.

- **Members.** Every pier, beam, joist, sheet, plate, stud, header, rafter, batt and board is a piece: `{ id, struct, storey, kind, type, stage, parent, built, material, section: { b, d }, length, a, b, y0, y1 }`, sheets and batts also `area` and `thickness`, concrete and gravel `volume`. Kinds: `site`, `pier`, `skid`, `footing`, `stemwall`, `slab`, `beam`, `post`, `joist`, `plate`, `stud`, `header`, `rafter`, `sheathing`, `membrane`, `cladding`, `roofing`, `insulation`, `lining`. The wall, floor, roof plane, gable infill or foundation (`<floor id>.fd`) they make up is their `parent`, lists them in `members`, and is `built` when they all are. Member ids are the parent's id plus a code and a running number (`p4.st7`); they are regenerated when their parent changes shape.
- **Stages**, in order (`__build.STAGES`, `__framing.STAGES`, and the same list in `src/sim/content/construction.js`): `site`, `foundation`, `floor-frame`, `subfloor`, `wall-frame`, `top-plates`, `roof-frame`, `roof-deck`, `dry-in`, `roofing`, `sheathing`, `wrap`, `openings`, `cladding`, `gutters`, `rough-in`, `insulation`, `lining`, `finish` (shown as "Tape and mud"), `carpentry` ("Trim carpentry"), `decorate` ("Paint"), `trim-out`, `services`. Doors and windows carry `stage: "openings"` and `parent` (their wall); fixtures, wires and pipes `stage: "services"`. `rough-in` and `trim-out` are tallied by the `services` system (`by: 'services'`, through `construction.setExternal`); `site` and `foundation` are the foundation view's when the building has a slab, poured piers or a stem wall (they carry a `hint` and no `by`). Stage wording, `needs` and `parentFirst` live in the content file.
- **Built state.** `setConstructionMode(bool)` (off by default: everything drawn is built). When on, new pieces start planned. `setBuilt(ids, bool)` takes member ids or the id of a wall, floor, roof plane or foundation; `setStageBuilt(structId, stage, bool)`; `setAllBuilt(bool)`; `showStage(stage | null)` chooses which stage's planned members are ghosted (default: the earliest unfinished one). Saved per structure as `plan` (the ids still planned). Building a `site` member levels the ground; until then a planned building does not touch the terrain.
- **Layers follow what is built.** A framed wall reports, outside in, `cladding`, `wrap`, `sheathing`, then `cavity` (air) or `insulation`, then `lining`: only those whose members are all built, and nothing at all until its studs are. Floors and roofs the same. Layer materials are registry ids where build mode has no appearance name (`osb`, `housewrap`, `fibreglass_batt`, `concrete`, `gravel`).
- **Which walls are framed.** Walls of the `timber` and `dark` appearances are stick-framed. Stone, brick, plaster, half-timber and log walls, towers, stairs and pillars have no members yet: each is one piece with its own `built` flag.
- **Foundations** per building (`found` in the save; `setFoundation(structId, type)`): `pier-blocks` (default for new buildings), `skids`, `piers`, `stemwall`, `slab`, and `plinth` (`FOUNDATIONS[type]` in `framing.js` gives name, `drop` and note; `slab`, `piers` and `stemwall` are the types a `foundation` job builds, the others stay plain members). Frost depth for footings comes from the climate: `FROST_DEPTH_M` in `content/concrete.js` (temperate 1.2 m, cold-continental 1.35, mediterranean-coast 0.45), read by `foundationRead.frost(state)`; poured piers and stem-wall footings are dug to it, or to the plan's own depth if deeper, and the job keeps the figure it was planned with in `job.frost` (what every building had before, and what saves without the field keep). A building stands `FOUNDATIONS[type].drop` above its levelled ground.
- **Shopping list.** `materialsList(structId?)` -> `[{ stage, itemId, qty, unit, label, why, count, missing? }]` in stage order; `itemId` is null where `src/sim/items.js` has nothing to sell yet (`missing` says what).
- **Plans.** `plans()` and `placePlan(id, x, z, yawRad)` -> `{ struct, pieces }`: `shed` (2.4 x 3.0 m) and `cabin` (3.6 x 4.8 m). They are off the metre grid, so their walls are free-angle wall pieces and their roofs have fractional bounds.
- **Fixtures and connections** are as specified above, with these additions: a fixture piece also carries `type` (= `fixture`), `name`, `category`, `system`, `b` (= `a`), `width`, `depth`, `height`, `rotationRad` (= `yawRad`), `mount` (`ground` | `floor` | `wall` | `roof`), `on` (the piece it is mounted on), `stage`, `built`. `yawRad` is three.js `rotation.y`: the front of the fixture points to world `(sin yaw, cos yaw)`; `settings.azimuthDeg` is clockwise from north and is kept in step with it. On a roof plane `settings.tiltDeg`, `settings.azimuthDeg` and `settings.roofPieceId` are set from the plane (a gutter also gets `settings.lengthM`). A wire's `gauge` is an AWG number (0 for 1/0), default 12; a pipe's `diameterMm` defaults to 19 (150 for a flue, which is a `pipe` of material `steel`). Connections also carry `a`, `b`, `y0`, `y1`. `setFixtureCatalog(map)`, `addFixtures([{ fixture, x, z, y?, yawRad?, mount?, settings? }])` -> ids, `setFixtureSetting(id, key, value)`, `connect(a, portA, b, portB, opts?)` -> `{ ok, id }` or `{ ok: false, reason }`, `removeFixture(id)`. ## One ground (ground A1-A2)

The walked surface is `base(x, z) + macro + fine`:

- `base`: the engine's untouched terrain (`baseHeight`, noise plus river carving), handed to the sim with `setGroundBase(fn)`. Pure of the seed.
- `macro`: an earthwork-format grid with points 1 m apart (tiles of 32 x 32, the same layout as a terrain chunk), owned by the `ground` system in `sys.ground = { v, macro, rev, totals, pending }`. Machine scale, building pads, the brush.
- `fine`: the 10 cm earthwork grid (`sys.landscape.grid` until slice A5 moves it to `sys.ground.fine`). Hand scale: spade, trench, footing.

Generic code: `src/sim/core/ground.js` (`cut`, `fill`, `push`, `tamp`, `gradePad`, `trimTo`, `conform`, `absorb`, `importTile`, `tileMetres`, `surfaceY`, `gradedY`; regions `{ poly } | { path, w } | { at, r } | { near, r }`). It reuses `core/earthwork.js` unchanged at either step (`push` now also takes a level function). A footprint narrower than 0.75 m works the fine grid; wider works the macro grid and first absorbs the fine ground under its core, folding that volume into the operation (volume is conserved across both grids). `payload.on: 'macro' | 'fine'` overrides the routing.

The system `src/sim/ground.js` (`groundSystem({ fineOf, tampBits })`, before `landscape` in `GAME_SYSTEMS`) is the one command API for moving earth. Every command returns `{ ok, ... }` or `{ ok: false, reason }` and changes nothing on failure:
`ground.cut { x, z, r, m3, maxDepth?, bare?, on? }` -> `{ m3, s, on }`; `ground.fill { x, z, r, m3, surface?, layer?, on? }` -> `{ m3, on }`; `ground.push { x0, z0, x1, z1, w, level | levelY }` (relief or world height; the ridge settles on the next tick); `ground.grade { samples, targetY, core, rim, pit?, absorb? }` -> `{ cutM3, fillM3, tiles }` (build mode's site-cut maths: within `core` of a sample the ground goes to `targetY`, blending back by `rim`); `ground.trim { region, targetY }` (fine ground cut down to a level); `ground.tamp { x, z, r, passes }`; `ground.importMacro { key, b64 }` (the engine bridge only). Event `ground.macro { keys }` after any macro change; fine changes bump the fine grid's `rev` (and a macro change under fine tiles does too, so the Yard redraws). Reads: `groundRead.surfaceY / gradedY / relief / conform / macroTile / macroKeys / netVolume (state, ...)`. Tests: `test/ground.test.mjs` (conservation at both steps, pad maths identical to the old site cut, a quarry fixture with no homestead content).

Engine (`src/engine.js`): `world.edits` is now a mirror of the macro grid. `syncMacro` copies changed tiles on `ground.macro` and `loaded`, updates the chunk heights at once (so `heightAt`, `groundAt` and wheels see new ground the same frame) and rebuilds chunk meshes at most every 120 ms. Old writers (`applyBrush`, the starting well, build mode's `cutTerrain` through `editSet`) still write `world.edits`; `setDelta` marks the tile and `flushMacro` (start of `syncSite`, before every advance and save) imports it. Add-ons: `window.__game.ground = { read, cmd(name, payload), surfaceAt(x, z), rev, verify() }`. `heightAt(x, z)` is the graded ground (base + macro); `ground.surfaceAt` adds the hand-shaped fine ground; `groundAt(x, z, y)` adds built floors on top. `verify()` diffs mirror and truth (`{ tiles, maxDiff }`).

Build mode's site cut (`cutTerrain` in build.js, A3) is `ground.cmd('grade', ...)`; the old `editSet` loops remain only as a fallback. `ground.grade` absorbs the fine ground over the whole levelled pad (every macro cell that ends at least half way to the target), so a hand-dug hole under a new building is filled when its site is done.

## Foundations and concrete (B1)

- Generic `src/sim/core/cure.js`: a cast material's cure record `{ ageH, setP, set, eqH, strength, cap, frost, dry, pit, covered, wet, tc }`. Initial set on clock hours (`setH20` at 20 C, doubling per 10 C colder); maturity as Nurse-Saul equivalent age (datum -10 C, 20 C reference) on the seasonal clock (`ctx.lifeDt`); strength fraction by ACI 209 `te / (4 + 0.85 te)` (te in days) times `cap`; frost while below 3.5 MPa and drying (ACI 305 evaporation above 0.5 kg/m2/h in the first day, bare and dry) lower `cap`. Hydration adds 5 C the first equivalent day, an insulating cover 8 C more. Test: `test/cure.test.mjs`.
- Content `src/sim/content/concrete.js`: design strength 25 MPa, bag yield, set time and `WORKABLE_SCALE`, `CURE_GATES` (walk 0.10, strip 0.20, frame 0.50, backfill 0.70, drive 0.75), `GATE_SAYS`, `GATE_HOLDS` (the frame gate holds every construction stage that stands on the foundation).
- System `foundation` (`src/sim/foundation.js`, after construction in `GAME_SYSTEMS`, every 10 ticks): `sys.foundation = { v, nextId, jobs, carry, machines }`, one job per building with a slab, poured piers or a stem wall (see docs/design/ground-foundations.md 3.3). Commands: `foundation.setPlan { structId, type?, elements? }` (without elements they are read from the building's construction members: the concrete ones become elements, the gravel ones the base), `foundation.forget`, `foundation.debugPour { jobId | structId }` (sandbox: poured now, the foundation members are settled in construction, the cure starts). The step cures poured jobs with the weather's air, wind, humidity and rain, emits `foundation.gate { jobId, gate }` and `foundation.cured`, and keeps construction's holds in step (it puts them back if a plan is sent again). Reads: `foundationRead.job / jobFor / gates / cureOf / jobView`.
- **`pr.keep`** (wave 2 X2, `src/sim/core/keep.js`): what other systems keep on a building's progress record lives in one bag, `pr.keep[source]` (`keep.hold[stage]`, `keep.ext[stage] = [built, total]` for work another system tallies, `keep.extLines[source] = { sig, lines }` for its shopping lines). `setPlan` rebuilds the record and carries the whole bag over, so a new source needs no change in construction; `keepOf(pr)` and `kept(pr, source)` read it (older saves kept `ext`, `extLines` and `hold` on the record itself: moved under `keep` on first read). Test: an unknown key survives a resent plan. Never hand-copy a foreign field in `setPlan`.
- Construction: `construction.setHold { structId, stage | stages, reason | null }` stores `pr.hold[stage]`; a held stage is not open and `blocked` returns the hold's text, which `install` returns with `held: 1` and the construction view shows as it is.

## Adding to build mode

`src/build.js` is one large closure (about 11,300 lines) that several sessions edit at once. Do not split it or reorganise it. New building elements (decks, porches, lofts, skylights, chimneys) go in new files and register through the extension point (X1): `src/build-ext.js` (loaded just before `build.js`; `build.js` calls it at a few fixed places) and `__framing.register`. A file of its own is added to `build.sh` after `build` and `buildui`.

- Members: `__framing.register(kind, fn(out, el, desc, h))`. `generate` runs a fourth loop over `desc.extras` after floors, walls and roofs; `fn` pushes the members of one element `el = { kind, id, ... }`. `h = { M, LUMBER, SHEET, FLOOR_T, splice, sheetRows, spans, STAGES }`; `h.M(out, id, kind, type, stage, parent, material, b, d, a, b, n, extra)` is the same member maker the walls use. Use the existing kinds (`post`, `beam`, `joist`, `sheathing`...) where they fit, so `materialsList` buys them and construction knows them; `parent` is the element's piece id.
- `__build.extend({ id, describe?, pieces?, draw?, tools?, inspector? })`, id lower-case letters, digits and dashes. Registering again with the same id replaces it; standing buildings are redrawn with it. Every hook gets `h.data` (this building's `S.ext[id]` or null) and `h.pid(key)` (a piece id `x-<ext>-<struct>-<key>`: unique across buildings, stable through saves and undo, never read as a build-mode `p<n>` id; copies of a building get new ones).
  - `describe(S, desc, h)`: called in `membersOf` after walls, floors and roofs are filled. Push elements into `desc.extras`, or add to `desc.roofs` (a porch roof). `h` also has `H` (wall height), `yo`, `up(y)`, `groundY(x, z)`, `toWorld(x, z)`. Coordinates are the building's own metres.
  - `pieces(S, out, h)`: called in `structPieces` before members are attached, so a piece you push (`{ ...h.head(id, kind, type, material), a: h.W2(x, z), b, y0, y1, ... }`) gets `members` and is built when they all are. Also `h.loop`, `h.y0`, `h.H`, `h.up`.
  - `draw(S, add, mem, st, h)`: at the end of `drawMembers`, for what is not plain members (members are drawn, ghosted and staged by build mode already). `add(mesh, roof?)` puts a mesh in the building; its geometry is disposed on the next redraw, so share materials.
  - `tools: [{ id, name, icon?, title?, hint?, group?, cat?, letter?, options?(g, G_), choose?(key, v), down?(hover, e), hover?(hover) }]`: a tool in the slot bar (`cat` is the slot, as build.js's TOOLS: `more` unless it says, so a deck is in More's flyout; `icon` is SVG markup on a 24 x 24 grid; `title` is the slot's tip), `letter` a capital build mode leaves free (the deck takes H), the hint line, the tray and inspector (controls whose ids are `x:<tool>:<key>` come back to `choose(key, v)`; a group goes in the tray unless it carries `sec: "<section>"`, which puts it in the inspector), a click on the world (`hover.F` is the building or a new one, `hover.lx/lz` local metres) and pointer moves. The bar redraws its slots when an extension registers after it was built.
  - `inspector(g, G_, key)`: fills the options strip under the Select tool after `__build.extSelect(id, key)` (null clears), while build mode has nothing of its own selected.
- Data: `__build.setExt(structId, id, data)` stores a copy of plain JSON in `S.ext[id]` (null removes it), pushes an undo step and rebuilds; `__build.getExt(structId, id)` reads a copy. `S.ext` is serialized with the structure (undo, save, copy). Data of an extension that is not loaded is kept as it is.
- An extension hook that throws is reported (console.error) and skipped; the building is still drawn.
- Picking, walking and structures of their own (B-2): `pick?(S, R, h)` returns `{ t, key, id? }` for the extension's own piece under the pointer (`R` is the ray in the structure's frame, y from `S.y0`; `h.hitBox(R, x0, y0, z0, x1, y1, z1)`); a Select click on it calls `__buildExt.select(ext, key)` (its `inspector` shows) and Delete calls `remove?(key)`. `bounds?(S, h)` returns local points that widen the structure's extent (picking and the ground read find it). `ground?(S, lx, lz, y, h)` returns a walking surface in the structure's y (or null): `__build.ground` takes it. `__build.extCreate({ ox, oz, yaw, y0 }, id, data)` makes a structure holding only extension data (a free-standing deck); `setExt(..., null)` that empties one removes it. Members may carry `buy` (what `buyAs` would return) and `hw: [[itemId, qty, unit, label, why]]` (hardware lines per stage, like nails).
- Limits now: ground levelling ignores extension elements; picking draws no highlight for an extension's piece (the deck shows its own rectangle only while drawing).
- Decks (`src/game/deck.js`, bundled with `src/sim/content/deck.js`): see docs/PLAYTEST.md, wave 2 B-2. Smoke: `node test/deck.smoke.mjs`; headless `test/deck.test.mjs`.

## Module layout and ownership for the waves

New simulation code goes in `src/sim/<system>.js`, one system per file, registered in `src/sim/index.js`. New interface code goes in its own add-on file under `src/` and is added to the module list in `build.sh`. Parallel iterations each own their files and touch shared files (`index.js`, `build.sh`, `template/head.html`, `ARCHITECTURE.md`) only to add their own line, so merges stay mechanical.

## Testing

- `npm test`: headless simulation tests under `test/*.test.mjs` (Node's test runner, no browser). Takes about 45 s on a 2-core machine since the 19 Nov sim speed-up (it was 3 to 5 minutes). While iterating, run one file: `node --test test/<name>.test.mjs`.
- `node test/page.smoke.mjs`: loads the built page in a headless browser and checks that it loads without errors, Low and High quality render, build mode opens, time controls work, a save survives a reload, and the simulation's frame cost is in budget.
- `node test/build.smoke.mjs`: builds a house in build mode through pointer events and checks the piece list, typed sizes, selection and remodeling, undo, the save round trip, and the bar on a phone.
- Page tests share `test/helpers/page.mjs` (launch, small Low-quality window, `__game.stepFrames(n)` instead of wall-clock waits). Wall-clock budget asserts run only with `BENCH=1`. The other smokes (foundation, services, services-water, trailer, vehicles, build-ext, ui, landscape core and tail) are listed with when to run each in `CLAUDE.md`.
- Frame rate itself can only be judged on a real GPU; the smoke test measures the simulation's cost per frame instead.
